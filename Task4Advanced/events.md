# Каталог событий

Событие — зафиксированный факт, а не приказ другой системе и не копия строки DWH. В таблицах ниже указаны целевые контракты. Имена, сроки хранения и SLO — проектные решения; их нужно согласовать с владельцами до запуска.

## Общий конверт

| Поле | Назначение |
|---|---|
| event_id | UUID факта; не меняется при повторной доставке |
| event_type, schema_version | Имя и версия схемы полезной нагрузки |
| producer, tenant_id, region | Владелец факта и граница организации/размещения |
| aggregate_type, aggregate_id, aggregate_version | Локальная сущность, ключ и монотонная версия её изменений |
| occurred_at | Время фиксации факта в источнике, UTC; не время доставки |
| correlation_id, causation_id | Идентификаторы процесса и породившего сообщения, без персональных данных |
| classification | Класс данных; проверяется политикой издателя и брокера, не даёт прав сам по себе |
| payload | Только поля зарегистрированной схемы; неизвестные поля не разрешены |

Ключ партиции: tenant_id + aggregate_type + aggregate_id. Порядок есть в рамках партиции, а не всей компании. Потребитель проверяет aggregate_version, пропуски и повторы; для нескольких агрегатов используется процесс с собственной корреляцией. DataProductPublished ключуется по product_id и организации.

## Операционные факты

Указанные поля payload дополняют общий конверт. Идентификаторы пациента, договора и исследования считаются ограниченными данными даже без ФИО. Топики разделены по контурам; общий портал не подписывается ни на один из перечисленных операционных топиков.

| Событие / производитель | Минимальный payload | Потребители | Область |
|---|---|---|---|
| PatientRegistered / Реестр пациентов | patient_id, registration_channel | Запись, Медицинская помощь | Клиническая; контакты остаются в API реестра |
| PatientConsentChanged / Реестр пациентов | patient_id, purpose, consent_version, status | Только сервисы соответствующей цели обработки | Клиническая; не является единственным механизмом отзыва доступа |
| CapacityReserved / Запись | reservation_id, resource_id, slot_start, expires_at | Процесс создания записи | Внутренняя клиническая |
| CapacityReleased / Запись | reservation_id, reason_code | Процесс записи | Внутренняя клиническая |
| AppointmentReserved / Запись | appointment_id, reservation_id, patient_id, clinic_id, tariff_id, expires_at | Расчёты клиник | Клиническая; tariff_id не передаётся в BI |
| AppointmentConfirmed / Запись | appointment_id, reservation_id, invoice_id | Уведомления, операционное расписание | Клиническая |
| AppointmentCancelled / Запись | appointment_id, reservation_id, reason_code | Расчёты, уведомления | Клиническая; свободного медицинского текста нет |
| InvoiceIssued / Расчёты клиник | invoice_id, appointment_id, amount_minor, currency | Процесс записи, платёжный адаптер | Клиническая финансовая |
| InvoicePaid / Расчёты клиник | invoice_id, appointment_id, payment_id, amount_minor, currency | Запись, локальная финансовая проекция | Клиническая финансовая |
| RefundIssued / Расчёты клиник | invoice_id, payment_id, refund_id, amount_minor, currency | Процесс отмены, локальная финансовая проекция | Клиническая финансовая |
| CreditAgreementCreated / Кредитование | agreement_id, borrower_ref, principal_minor, currency, terms_version | Банковский учёт, банковский комплаенс | Банковская; borrower_ref не patient_id |
| CreditDisbursementRequested / Кредитование | agreement_id, operation_id, account_ref, amount_minor, currency | Банковский учёт | Банковская; намерение выдачи после бизнес-проверок, но ещё не факт перевода |
| FundsDisbursed / Банковский учёт | agreement_id, operation_id, posting_id, amount_minor, currency | Кредитование, банковская финансовая проекция | Банковская |
| DisbursementRejected / Банковский учёт | agreement_id, operation_id, reason_code | Кредитование | Банковская; без свободного текста проверки клиента |
| MaterialReservationRequested / Производство | reservation_id, order_id, items: sku_id + quantity + unit | Снабжение | Производственная; количество строго положительное |
| MaterialsReserved / Снабжение | reservation_id, positions: warehouse_id + sku_id + lot_or_serial_id + quantity | Производство | Производственная; только после полного резерва |
| MaterialReservationRejected / Снабжение | reservation_id, reason_code | Производство | Производственная |
| StockAdjusted / Снабжение | warehouse_id, sku_id, lot_or_serial_id, delta, unit, reason_code | Локальная проекция остатков и сверка | Производственная |
| BatchReleased / Фарма | batch_id, product_id, specification_version, quantity, unit | Снабжение, прослеживаемость | Производственная; протокол испытаний остаётся у владельца |
| BatchRecalled / Фарма | batch_id, recall_id, reason_code | Снабжение, прослеживаемость | Производственная |
| DeviceReleased / Электроника | serial_number, model_id, specification_version | Снабжение, прослеживаемость | Производственная; без телеметрии пациента |
| DeviceRecalled / Электроника | serial_number, recall_id, reason_code | Снабжение, прослеживаемость | Производственная |
| AIResearchCompleted / Медицинский ИИ | research_id, model_version, result_version, result_ref | Только Медицинская помощь | Изолированная медицинская; result_ref — непрямой идентификатор, не публичный URL |
| AIResearchFailed / Медицинский ИИ | research_id, model_version, error_code | Медицинская помощь, операционный разбор | Изолированная медицинская; без входного документа/stack trace |
| FinancialPeriodClosed / Корпоративные финансы | period, currency, revision, totals_ref | Финансовый продукт головного офиса | Корпоративная финансовая; только сводки юридических лиц |
| FinancialPeriodCorrected / Корпоративные финансы | period, currency, previous_revision, revision, totals_ref | Финансовый продукт головного офиса | Та же область, корректировка не перезаписывает прошлую версию |

Для запросов MaterialReservationRequested и CreditDisbursementRequested один назначенный обработчик исполняет действие, остальные потребители могут только наблюдать. Это факты зарегистрированного запроса; они не трактуются как уже успешный резерв или выдача. Синхронное API принятия команды возвращает «принято», а не «исполнено».

## Публикация продуктов данных

| Событие | Производитель → потребители | Payload |
|---|---|---|
| DataProductPublished | Доменные сборщики → каталог, разрешённые корпоративные проекции | product_id, version, schema_ref, dataset_ref, checksum, period_start, period_end, source_watermark, dimensions, quality_status |
| DataProductWithdrawn | Владелец продукта → каталог, все подписчики версии | product_id, version, withdrawal_id, reason_code |

dataset_ref — внутренний идентификатор набора, не подписанный URL и не ключ доступа. Каталог выдаёт доступ отдельно с проверкой прав пользователя, региона и версии. Даже получив событие, потребитель не получает доступ к файлу автоматически.

Примеры продуктов: clinic_capacity_daily (суммы доступных/занятых слотов по филиалу, без пациентов и специализации), clinic_turnover_daily (суммы в валюте по юридическому лицу), bank_portfolio_monthly (агрегаты портфеля без заёмщиков), production_output_daily (выпуск по предприятию и продукту), inventory_daily (допущенные остатки), ai_resource_cost_monthly (стоимость ресурсов без исследований). Период — полуинтервал [period_start, period_end). Корректировка создаёт новую версию с прежним периодом, а потребитель заменяет текущую версию, а не прибавляет полный срез второй раз.

Ни одно поле не должно содержать диагнозы, тексты заключений, результаты исследований или ссылку/идентификатор для восстановления этих данных. Проверяется не только имя поля, но и разрешённый источник продукта. Нельзя переименовать medical_record в payload и считать ограничение выполненным.

## Доставка, совместимость и ошибки

1. Доменная транзакция записывает агрегат и outbox. Издатель публикует outbox через CDC либо поллер с повторами. У старого SQL Server 2008 CDC и совместимость коннектора не предполагаются: адаптер использует поддерживаемый экспорт/прикладной журнал с контрольной сверкой. Он помечает происхождение legacy и не изображает бизнес-факт без нужной семантики.
2. Доставка end-to-end — at least once. Потребитель атомарно сохраняет результат и event_id в inbox своей БД, затем подтверждает offset. После сбоя повтор даёт прежний результат. Для внешних операций передаётся стабильный idempotency key; отсутствие поддержки требует сверки результата перед повтором.
3. Операционные сообщения и дедупликационные ключи хранятся согласованное окно повторной доставки. Предварительная настройка пилота — 7 суток брокерного retention; inbox живёт не меньше retention плюс максимальное окно ручного replay и восстановления. Финансовые operation_id защищаются уникальным ограничением на весь срок жизни операции. Массовый старый replay выполняется в отдельной проекции, а не через повтор денежных побочных эффектов.
4. Схема регистрируется до выпуска. Неизвестные поля запрещены относительно указанной schema_version; валидатор публикации выбирает именно эту схему. Потребитель принимает только согласованный диапазон версий. Необязательное новое поле допускается без нового major только после проверки совместимости всех поддерживаемых потребителей; строгим потребителям сначала обновляют разрешённую схему. Удаление/смена смысла поля — новый major контракт, период двойной публикации и явное отключение старого. В схеме нет произвольных maps с медицинским текстом. Критерии совместимости проверяются на контрактах потребителей.
5. Временная ошибка — ограниченные повторы с увеличением интервала. Повреждённый контракт, неизвестная классификация или постоянная ошибка — защищённая DLQ своего домена и сигнал владельцу. Для критических последовательностей тот же aggregate_id приостанавливается до разбора; обработка следующей версии не скрывает пропуск.
6. В журнал ошибок и мониторинг идут event_id, код ошибки и метаданные без payload. В медицинской DLQ остаются те же ограничения, что у исходного топика. Повтор запускает владелец после исправления причины и с тем же event_id. Нельзя скопировать медицинскую DLQ в общий dashboard.
7. Сверка сравнивает число и суммы фактов по периоду в источнике и проекции. Freshness, outbox lag, DLQ depth, пропуски версий и расхождения выводятся раздельно. Предварительная цель пилота — задержка разрешённых оперативных проекций до 5 минут в 95% случаев; финансовый закрытый период публикуется только после сверки.

Изменение согласия или отзыв продукта блокирует новые чтения через авторизационный сервис сразу после фиксации; событие помогает очистить кэши, но не заменяет проверку актуальных прав. Удаление из брокера, резервных копий и производных наборов выполняется отдельной процедурой жизненного цикла с учётом обязательного хранения; бессрочное хранение сырых событий не закладывается.

Механика реализации опирается на [outbox router Debezium](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) и [границы гарантий доставки Kafka](https://kafka.apache.org/35/design/design/). Inbox, сверки, права и бизнес-инварианты остаются ответственностью приложения, а не свойством одного брокера.
