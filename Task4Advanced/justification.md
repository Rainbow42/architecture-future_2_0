# Почему меняю интеграции

Общий DWH стал местом не только хранения, но и бизнес-логики. Новое направление зависит от изменений чужих таблиц, преобразований Camel и длинной очереди отчётов. Просто перенести SQL Server в облачную ВМ недостаточно: границы ответственности и стоимость изменений останутся прежними.

Выбрала доменную модель: владелец процесса фиксирует факт, а каждый разрешённый потребитель строит свою проекцию. Платформа даёт брокер, каталог, проверку схем, доступ, мониторинг и инструменты публикации. Формула выручки клиники или допуска партии при этом не переезжает в платформенную команду.

| Задача | Сейчас | Целевой подход и ограничение |
|---|---|---|
| Подключить купленное производство | Изменить DWH и центральные преобразования | Добавить контекст и продукт данных по контракту; модель банка не меняется |
| Получить свежий показатель | Дождаться общей пакетной обработки | Обновлять локальную проекцию по событиям; допустимая задержка видна пользователю |
| Увеличить нагрузку одного бизнеса | Расширять общий узел | Масштабировать его обработчики и партиции; горячий ключ всё равно требует отдельного решения |
| Пережить сбой потребителя | Ошибка цепочки синхронных вызовов | Сохранить факт и догнать поток после восстановления; нужны retention, backpressure и сверка |
| Ограничить чувствительные данные | Права на общий набор таблиц | Отдельные контуры и разрешённые продукты; фильтр в BI не считается границей защиты |
| Исправить ошибочную витрину | Пересчитать общий отчёт | Перестроить конкретную проекцию из допустимого источника; старое событие не запускает повторную оплату |

## Что оставляю синхронным

Авторизацию чтения, принятие команды и проверку локального денежного/складского инварианта нельзя заменить надеждой на будущую обработку события. API проверяет права и сохраняет команду локально. Дальнейший междоменный процесс асинхронный; интерфейс показывает состояние ожидания и срок, а не преждевременный успех.

Kafka не делает банковские проводки атомарными с БД клиники. Система должна переносить повтор и задержку, отличать отказ от неизвестного результата, поддерживать компенсации и разбор оператором. За это придётся платить дополнительными проекциями, наблюдаемостью и обучением команд. Для редких справочников и выгрузки закрытого периода оставляю пакетный обмен по версионированному контракту — поток нужен не везде.

## Переход без остановки бизнеса

1. За первые два месяца согласовать владельцев, словарь, разрешённые продукты и инварианты. Замерить текущий срок подключения источника, длительность отчёта и число расхождений; значения не придумываются заранее.
2. В 0–6 месяцев взять пилот расчётов клиник и загрузки филиалов. Адаптер старой системы выдаёт ограниченные факты; новая проекция работает рядом с существующим отчётом. Приёмка — одинаковые суммы, объяснимые отклонения, отсутствие запрещённых данных и понятная задержка.
3. В 6–18 месяцев переносить бизнес-операции по одному контексту. В каждый момент для операции есть только один пишущий владелец; параллельные проекции не означают двойную запись в старое и новое приложение. Резервные процедуры и обратное переключение проверяются до cutover.
4. В 18–36 месяцев отключать центральные преобразования и старые отчёты после сверки, периода наблюдения и подтверждения владельца. Camel и DWH остаются временными мостами для неперенесённых функций, а не обязательным транзитным узлом новых сервисов.

Пилот считается успешным, когда новый потребитель подключается без изменения производителя, повтор факта не удваивает расчёт, отключённый потребитель восстанавливает проекцию, а BI не может прочитать клинический топик или получить ссылку на исследование. Это критерии будущих испытаний, не заявление об уже проведённых тестах.
