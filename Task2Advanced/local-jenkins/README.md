# Локальный приватный CI

Контроллер Jenkins 2.580.1 запущен только на loopback. Анонимный доступ и регистрация отключены, inbound-порт агентов закрыт, исполнителей на контроллере нет. [Инициализация](init.groovy) читает `TF_CI_PRIVATE_ROOT`; пароль создаётся в приватном файле и не печатается. WAR и плагины получены из официального update center с проверкой SHA256.

Агент `future-terraform` — отдельная локальная Lima/VZ-машина Ubuntu 24.04 ARM64: 2 CPU, 2 ГБ RAM, разреженный диск 12 ГБ. Режим plain, mounts отсутствуют, автоматического проброса портов и containerd нет. Проверены список mount и отсутствие каталога конфигурации хоста. На хосте подтверждён включённый FileVault. Рабочие облачные профили и домашние файлы хоста агенту не передаются.

Внутри установлены Node.js 22.23.3, Terraform 1.12.2 и OpenJDK 21. Node и Terraform сверены с SHA256 из официального источника/зеркала Yandex Cloud; Java — из репозитория Ubuntu. Агент подключён через stdio SSH с закреплённым host key, без публичного Jenkins endpoint. Launcher очищает окружение, задаёт отдельные HOME/PATH и отключает пользовательскую конфигурацию Git. [Регистрация агента](agent.groovy) рассчитана на доверенного администратора локального Jenkins; не принимает команды из PR.

Состояние контроллера, пароль, SSH-ключ Lima и планы находятся вне репозитория. Полные журналы не публикуются. На агенте один executor. Проверочный job `future-agent-check`, build 1, завершился SUCCESS: Node/Terraform/Java выполнились на Linux-агенте, проверка отсутствия конфигурации хоста прошла. Это smoke-run без облачных credentials, не выполнение Terraform deployment pipeline.

Jenkinsfile действительно принят Declarative Pipeline linter: `Jenkinsfile successfully validated.` По отдельному разрешению в локальные Credentials установлены отдельные ключи чтения плана/применения Compute и свои S3-ключи сред; созданы три deployment jobs. На агенте хранится приватный JSON с фиксированными несекретными настройками, а имя job связано с его средой. IAM-токен запрашивается заново перед каждой стадией через PS256; заранее сохранённый токен не пережидает input. Первые два dev-запуска выявили несовместимые с sandbox Groovy-вызовы до выдачи credentials; они исправлены без отключения защиты.

Итог настоящих deployment: stage build 1, prod build 2 и dev build 4 — SUCCESS; ВМ, диски, закрытые SG и outputs каждой среды сверены с API и KMS state. Предыдущие частичные отказы dev на диске в зоне a и prod на квоте VPC сохранены в истории. После сверки guards архивированы с записью разбора, затем созданы новые планы, без повторного apply старых планов, state push или force-unlock. Prod переиспользует согласованную VPC stage; dev перенесён в зону d с отдельно согласованной заменой пустой подсети.

Отдельный future-release-stage build 1 удалил только проверенную stage-ВМ и её два диска по явному согласию, сохранив сеть и историю. Stage input владелица нажала самостоятельно, prod/dev inputs нажаты делегированно по её разрешениям; независимого второго проверяющего нет. Удаления требуют отдельного согласия, административный API для input не используется. После истечения браузерной сессии применялся обычный повторный вход, CSRF-защита не отключалась. Подробные результаты и ограничения — в [отчёте](../../docs/deployment-results.md).
