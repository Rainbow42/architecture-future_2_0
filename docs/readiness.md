## Сквозные ограничения

- Медкарты, истории болезни и результаты исследований исключены из портала, общего хранилища, продуктовых событий и аналитических логов/DLQ. Клинические процессы остаются изолированными.
- Домены владеют формулами; платформа проверяет продукт и фиксирует версию/outbox. Сборщик не обходит этот путь прямой публикацией в Kafka.
- Отзыв блокирует чтение в каталоге до доставки события. Новая витрина доступна после загрузки; составной отчёт использует совместимые периоды.
- Миграция идёт с одним писателем и сверкой. Возврат после новых записей требует переноса накопленных изменений.
- Учебные Terraform-ВМ не являются развёрнутой отказоустойчивой платформой из C4. Mock-планы не подтверждают создание ресурсов.
- В TCO переход дороже текущего состояния на 58,52 млн ₽ за три года. Высвобожденные 32 520 часов уже учтены; окупаемость не заявляется.

## Условия реальной проверки и отправки

1. Учебный облачный каталог и расходы в пределах гранта согласованы. Созданы раздельные Compute-identities для чтения и применения, свои S3-identities сред; ключи в приватном локальном CI. SSH-пара подготовлена, в jobs только открытый ключ; сеть не расширять без согласования. KMS/preflight/S3/lock проверены, временные права настройщика отозваны. Stage build 1 после ручного input владелицы завершился SUCCESS: ВМ RUNNING, диски READY, ресурсы и outputs совпали с зашифрованным remote state. Dev build 3 сохранил три сетевых ресурса после отказа создания диска в ru-central1-a; guard не снят. Prod build 1 частично отказал на квоте VPC; его data-диск сохранён в state. Разрешено переиспользовать VPC stage и подготовить ограниченную очистку stage compute, без самого удаления. Пароли и закрытые ключи в чат не передаются.
2. Для dev нужна экономная стратегия восстановления: в ru-central1-d stage уже занимает 2 vCPU и 14 ГБ HDD из квоты 2 vCPU/20 ГБ; новая dev-ВМ с дисками 12 ГБ туда одновременно не помещается. Не удалять stage или его диски без отдельного решения владелицы. До восстановления dev не повторять старый план, не делать state push или force-unlock. После сверки state и нового prod-плана с согласованной VPC обычное create/update можно подтвердить делегированно. Для stage cleanup отдельно согласовать фактическое удаление после просмотра точных целей. Сохранить несекретные подтверждения; полные plan/state/логи в публичные артефакты не загружать.
3. Доступ к заданию восстановлен, теория и личный опрос завершены; форма сдачи доступна. При новой необходимости входа не обходить ограничения безопасности.
4. Явный зачёт спринта 10 уже получен в Практикуме; повторная проверка или отправка десятого не нужна.
5. Повторить [проверки репозитория](checks.md) после изменений. По последнему прямому указанию пользовательницы отдельный просмотр PR и подтверждение сдачи не требуются.
