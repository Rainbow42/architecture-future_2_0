# Техрадар

Радар относится к «Будущему 2.0», а не ко всем возможным проектам. Adopt означает выбор для целевого решения, не утверждение, что технология уже развёрнута и проверена в компании. Trial — ограниченный пилот с критериями; Assess — сначала исследование; Hold — не расширять применение, выводить постепенно или не использовать в этой задаче. Названия колец оставила как в задании.

Структуру «тип решения + кольцо» взяла из [подхода Thoughtworks](https://www.thoughtworks.com/radar/faq). Размещение ниже — моя оценка условий проекта, не переписанный рейтинг поставщика.

## Карта решений

| Область | Adopt | Trial | Assess | Hold |
|---|---|---|---|---|
| Архитектурные подходы | A1 Доменные контракты; A2 Outbox/inbox; A3 Изоляция данных и проверка прав; A4 Strangler / ACL | T1 Продукт данных end-to-end | S1 Федеративное управление в нескольких регионах | H1 Общий DWH с бизнес-логикой; H2 Общий raw lake; H3 Сквозное exactly-once как допущение |
| Платформы | A5 S3-совместимое хранение; A6 PostgreSQL; A7 IAM / OIDC / MFA | T2 Kafka; T3 ClickHouse; T4 Облачная площадка с IaC | S2 Managed-сервисы против собственного сопровождения | H4 SQL Server 2008 для новой функциональности |
| Инструменты | A8 Terraform + review / ручной apply; A9 Контракты и аудит | T5 Совместимый CDC / экспорт; T6 Каталог с lineage и качеством | S3 Полноценный lakehouse / Iceberg | H5 Расширение общей шины Camel |
| Языки и приложения | A10 Java / Spring Boot; A11 Go и Python по существующим зонам | T7 React-портал; T8 Ограниченные витрины Power BI | S4 Дополнительный потоковый движок | H6 Новая логика в PowerBuilder; H7 Единый язык для всей группы |

## Adopt: что закладываю в основу

| ID | Решение и причина | Граница применения / проверка | Владелец |
|---|---|---|---|
| A1 | Bounded contexts и версионированные продукты: новая компания не должна менять общий DWH | Не превращать каждый контекст в отдельный сервис без необходимости; проверить владельца, ключи, схему и совместимость | Архитекторы доменов |
| A2 | Outbox, inbox, идемпотентность и сверка: сбои и повторы нормальны | Атомарность только внутри локальной БД; повтор внешнего платежа требует устойчивого ключа и проверки результата | Команды доменов |
| A3 | Отдельные клинический, банковский и корпоративный контуры; доступ закрыт при неизвестной политике | Нет медкарт, результатов, embeddings и ключей обратного join в аналитике; отрицательная матрица tenant/region/export | Безопасность и платформа |
| A4 | Постепенный перенос через Anti-Corruption Layer и единственного писателя | Для каждой функции сверка до переключения и отдельный возврат после новых записей | Команда миграции |
| A5 | S3 API для неизменяемых разрешённых наборов и копий | Совместимость проверяется для выбранного backend: права, версии, восстановление, условные записи и блокировки; S3 API не гарантирует равенство всех продуктов | SRE |
| A6 | PostgreSQL для каталога, политик и технических состояний | Не переносить в него бизнес-логику всей группы; отдельные схемы/роли и проверка восстановления | Платформа |
| A7 | Корпоративный IAM, OIDC и MFA | IAM подтверждает личность, платформа отдельно проверяет право на продукт, регион и экспорт | IAM и безопасность |
| A8 | Terraform, сохранённый plan, review и ручное подтверждение apply | Отдельные состояния сред, секреты вне Git, запрет применения чужого/устаревшего плана; пока подтверждены только проверки Task1 без облака | SRE |
| A9 | Контрактные проверки, качество продукта, технические метрики и аудит | Не логировать payload, токены и результаты запросов; версия без необходимых проверок не публикуется | Платформа и владельцы продуктов |
| A10 | Java / Spring Boot для API, публикации и загрузчика | Используется знакомая группе Java; конкретные версии и библиотеки фиксируются после проверки поддержки и безопасности | Команда платформы |
| A11 | Сохранение Go в банке и Python в медицинском ИИ | Не переписывать работающие системы ради единообразия; ИИ не получает публикацию результатов в общий BI | Банк и AI-команда |

## Trial: сначала проверить ограниченный сценарий

| ID | Пилот | Критерий перехода в Adopt | Кто принимает результат |
|---|---|---|---|
| T1 | Один разрешённый продукт клиники от источника до портала | Владелец, контракт, сверка, свежесть, отзыв и запрет чужого доступа работают; нет клинических полей ни в одном слое | Data Product Owner + безопасность |
| T2 | Kafka для публикаций и доменных событий в разных контурах | Повторы, отставание, replay и отказ узла не нарушают суммы; известны цена и время сопровождения. До этого допускается простой поллер outbox | SRE + команды доменов |
| T3 | ClickHouse для ограниченных агрегатных запросов | Нагрузочный профиль укладывается в цели Task3, новая версия видна целиком, права не обходятся. На малом пилоте допустим PostgreSQL до подтверждения необходимости отдельной СУБД | BI-команда + платформа |
| T4 | Облачная инфраструктура через Task1/Task2 | Разрешены расходы и размещение, init/plan/apply, блокировка state, SSH по согласованному пути и восстановление проверены в учебной среде | SRE + владелец бюджета |
| T5 | CDC на поддерживаемом источнике либо контролируемый экспорт легаси | Реальная версия источника совместима; дельта и повтор сверяются, нагрузка на клиники ограничена. Современный коннектор к SQL Server 2008 не предполагается | Команда легаси |
| T6 | Каталог, lineage и проверки качества | Для одной метрики можно найти владельца, разрешённый источник, трансформацию, версию и потребителей; отзыв виден в API и витрине | Платформа + Data Product Owner |
| T7 | React-портал самообслуживания | Пользователь получает разрешённый срез без заявки на SQL, видит свежесть и причину отказа; проверена доступность ключевых сценариев | Продуктовая команда портала |
| T8 | Power BI через одобренные витрины | У сервисной роли ровно нужный продукт и рабочее пространство; экспорт явно разрешён, процедура отзыва копий известна | BI-аналитик + безопасность |

Kafka, ClickHouse и портал показаны в целевой архитектуре Task3 как кандидаты выбранного решения. Кольцо Trial фиксирует, что ещё нет результатов пилота, а не противоречит их наличию в целевой схеме.

## Assess и Hold

| ID | Решение | Почему не внедряю сразу / когда пересмотреть |
|---|---|---|
| S1 | Федеративное управление региональными продуктами | В первые два месяца согласовать минимальные общие правила, затем пилот одного региона; расширять после проверки размещения и локальных владельцев |
| S2 | Managed Kafka/PostgreSQL/ClickHouse против self-hosted | Нужны доступность площадок, границы доступа, восстановление, контракт поддержки и сопоставимый TCO. Учебные VM не определяют выбор продакшена |
| S3 | Iceberg / lakehouse | Пока достаточно ограниченных версий продуктов и витрин. Исследовать при подтверждённых требованиях к нескольким движкам, большим повторным расчётам и управлению таблицами |
| S4 | Дополнительный потоковый движок | Не добавлять Flink/Spark только ради тренда; вернуться при сложных временных окнах и объёме, с которым простой загрузчик не справляется |
| H1 | Общий DWH как место всех бизнес-правил | Сохраняет зависимость всех изменений от одной команды; переносить правила по доменам, не добавлять туда новый бизнес |
| H2 | Общая сырая копия всех данных / векторный поиск по медкартам в BI | Противоречит запрету клинических данных в портале. Это не кандидат на Trial даже при удалённых ФИО |
| H3 | Предположение о сквозном exactly-once | Брокер не делает атомарными БД и внешний платёж; вместо обещания нужны идемпотентность, сверка и компенсации |
| H4 | SQL Server 2008 для новых функций | Устаревший источник остаётся только на переходе; перенос требует проверки экспорта и совместимости, а не новых зависимостей от него |
| H5 | Новые универсальные маршруты в общей Camel-шине | Увеличивают связанность; действующие маршруты выводятся только после переключения потребителей |
| H6 | Новые бизнес-правила в PowerBuilder | Продлит миграцию. Критичные исправления остаются допустимы до вывода функции |
| H7 | Переписывание всех сервисов на один язык | Не решает проблему владения данными и отвлечёт банк/клиники от целевых изменений |

Радар пересматривается по итогам пилота и каждого этапа роадмапа. Перенос между кольцами подтверждается результатом проверки, владельцем и решением; возраст технологии сам по себе не является результатом испытания.
