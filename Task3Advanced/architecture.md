# Целевая архитектура

## Почему не перенос общего DWH в облако

Сейчас SQL Server 2008 одновременно хранит данные и значительную часть правил бизнеса, PowerBuilder обслуживает процессы клиник, Camel связывает системы, Power BI читает подготовленную аналитику. Медицинский ИИ использует Python, банковские приложения — Go и Java. Появление фармпроизводства и медицинской электроники ещё сильнее увеличит число моделей и интеграций.

Перенос старого DWH на новые ВМ не уберёт зависимость изменений от одной команды. Поэтому выбрала доменные источники истины и версионированные продукты данных. Общая платформа не рассчитывает кредитные лимиты, не решает о выпуске партии и не интерпретирует исследования. Эти правила и проверки принадлежат соответствующим доменам.

Цель на первый год — рабочий портал самообслуживания и подключение согласованных продуктов основных бизнесов. Цель на три года — региональное масштабирование и подключение нового бизнеса через контракт, а не через переработку общего DWH. Горизонт двух-трёх регионов — из условия; число пользователей, пропускная способность и доступность нуждаются в замерах.

## Границы и источники истины

| Зона | Источник истины | Что может выйти в аналитику |
|---|---|---|
| Клиники | Доменные приложения и их БД; на переходе — ещё не перенесённые функции PowerBuilder/SQL Server | Сводная загрузка филиала без пациента и специализации врача, оборот юридического лица |
| Медицинская помощь и ИИ | Изолированные клинические хранилища, задания и результаты ИИ | Ничего из медкарт, истории болезни, исследований и их производных. Сводные расходы ИИ поступают из отдельного биллинга инфраструктуры без research_id |
| Банк | Кредитование и транзакционное банковское ядро | Согласованные агрегаты портфеля и финансовых оборотов, без заёмщика и его идентификаторов |
| Производство и логистика | Партии фармпродукции, серийные устройства, складские позиции | Выпуск, остатки и затраты по разрешённым справочникам; не телеметрия пациента |
| Корпоративные финансы | Сверенные сводки и версии закрытия периода | Консолидированные показатели, корректировки и статус сверки |

Клинический, банковский и корпоративный контуры используют разные сервисные роли и сетевые границы. Операционные брокеры клиник и банка не являются источниками общей подписки BI. Сборщик продукта работает внутри своего домена, читает только разрешённые ему источники и заранее агрегирует данные. Для медицинской помощи и результатов ИИ сборщика в общую аналитику нет.

До публикации владелец продукта и безопасность утверждают набор полей, размер групп, разрешённые срезы и способы объединения. Пока этого нет, продукт закрыт. Удаление ФИО не считается достаточным обезличиванием. Запрещены также тексты, embeddings, ссылки и ключи, позволяющие получить или присоединить клинические документы.

## Контейнеры платформы

| Контейнер | Технологический выбор | Ответственность и ограничения |
|---|---|---|
| Web-портал | React / TypeScript | Каталог, выбор показателей и срезов, заявка на доступ, просмотр свежести. В браузере нет ключей хранилищ |
| API портала | Java / Spring Boot | Проверка пользователя, правил продукта и региона, построение разрешённых запросов, ограничение объёма и аудит. Не принимает произвольный SQL |
| Каталог и политики | Java / Spring Boot + PostgreSQL отдельным контейнером | Владелец, версии схемы, lineage, публикации, качество, разрешения и отзыв. Пользователь не может самостоятельно выдать себе доступ |
| Сервис публикации | Java / Spring Boot, API и фоновые обработчики одного приложения | Строгая валидация входа, версии контрактов, запись неизменяемого набора, регистрация публикации и outbox. Не содержит правил расчёта бизнеса |
| Хранилище продуктов | S3-совместимое объектное хранилище | Только проверенные наборы разрешённых схем, версии и контрольные суммы. Нет зоны полных сырых выгрузок исходных БД |
| Брокер продуктов | Kafka | Уведомления о готовых и отозванных версиях, без самих медицинских или банковских операционных записей |
| Загрузчик витрин | Java / Kafka consumer | Идемпотентная загрузка готовой версии, сверка количества/хеша, отметка доступности; повтор не создаёт дубликаты |
| Витрины | ClickHouse | Разрешённые агрегаты по версии продукта и организации. Нет прямого пользовательского доступа; схема и фильтры задаются контрактом |
| Журнал аудита | Отдельное S3-хранилище с ограничением изменения | Решения о доступе, публикация и отзыв, пользователь, продукт, версия, объём. Не содержит SQL-результатов, токенов и payload доменных событий |

Корпоративный IAM — отдельная система с OIDC и MFA. Авторизация на продукт и срез выполняется платформой после аутентификации. PostgreSQL хранит каталог, политики и техническую машину состояний публикации, но не все бизнес-данные группы. Каталог, сервис публикации и API используют разные роли БД и разные API для записи.

Power BI сохраняется на переходе и получает только одобренные витрины через ограниченную сервисную роль API, привязанную к конкретному набору и рабочему пространству. Экспорт выключен по умолчанию. При включении владелец подтверждает, кто увидит копию и как она будет удаляться при отзыве; уже скачанный файл нельзя отозвать одним изменением роли. Прямой доступ Power BI к S3, PostgreSQL или клиническим БД не выдаётся.

## Публикация без «сырой зоны» запрещённых данных

1. Сборщик домена готовит разрешённый продукт локально. Невалидные или неподтверждённые данные остаются в карантине домена, не загружаются в общее хранилище.
2. Сервис публикации проверяет сервисную личность, владельца, активную версию контракта, типы и полный список полей. Неизвестное поле, запрещённый идентификатор или несогласованный срез приводят к отказу. Временная обработка проходит без сохранения payload в логи или общий staging; нельзя сначала положить весь dump, а потом удалить лишнее.
3. Проверенная версия записывается неизменяемым объектом по ключу domain/product/version/hash. Повтор с тем же ключом и содержимым возвращает прежний результат; другое содержимое под той же версией отклоняется.
4. Сервис фиксирует запись публикации и outbox в одной транзакции PostgreSQL. При сбое после записи объекта, но до транзакции каталог его не показывает; сверщик технических объектов удаляет незарегистрированные версии после установленного срока. До сверки у читателей нет доступа к этому ключу.
5. Outbox публикует DataProductPublished. Загрузчик проверяет манифест и хеш, записывает новую версию витрины и только затем отмечает её готовой. Пока версия не готова, API использует предыдущую допустимую версию и явно показывает её свежесть. Если такой нет — возвращает недоступность, не неполный набор.
6. При отзыве сначала блокируется версия в каталоге. Следующие запросы API и фоновые задания проверяют блокировку; событие инициирует очистку витрин и разрешённых экспортов. Срок жизни запроса ограничен, долгие выгрузки повторно проверяют разрешение перед выдачей файла. Kafka lag не отменяет запрет каталога.

Проверка схемы — необходимая, но не достаточная защита: чувствительные значения можно поместить в разрешённое текстовое поле. Поэтому свободные тексты не допускаются в общие аналитические контракты; категориальные поля ограничены справочниками, источники утверждаются отдельно, а новые продукты проходят проверку владельцем и безопасностью. Технический шлюз не заменяет эту ответственность.

## Запросы и самообслуживание

API извлекает организацию и роли из проверенной сессии и политики, а не доверяет переданному в форме tenant_id. Пользователь выбирает только опубликованные продукты, показатели и разрешённые измерения. Планировщик строит параметризованный запрос с обязательными фильтрами организации и региона; перед выдачей результата проверяет размер группы, разрешённые сочетания срезов и лимиты. Ошибки политики закрывают доступ.

Самообслуживание означает возможность выбрать уже разрешённый срез и запросить новый продукт, а не право менять бизнес-формулы или выполнять SQL к исходной системе. Заявка на расширение приходит владельцу домена, проходит проверку и выпускается отдельной версией контракта. Для составного отчёта планировщик выбирает готовые версии продуктов на общий согласованный период по манифестам; если совместимого среза нет, отчёт не выполняется. В интерфейсе показаны владелец, период данных, задержка и статус качества. Логи поиска и аудита не включают значения результата.

При недоступности IAM новая сессия не создаётся; действующая проверяется в пределах срока жизни и политики отзыва. При недоступности каталога новые запросы не выполняются: бессрочный кэш прав недопустим. Результат запроса выдаётся только после подтверждения записи аудита; сбой журнала не превращается в незаметный пропуск. Для изменений каталога и публикаций аудит ставится в надёжный outbox вместе с изменением состояния и доставляется с повторами. Сбой общей аналитики не останавливает запись пациента, лечение, банковские проводки или выпуск партии; накопление доменного outbox имеет лимиты и сигнал владельцу.

## Трёхлетний переход

| Этап | Что меняется | Условие выхода |
|---|---|---|
| Первые два месяца | Инвентаризация процедур DWH и Camel, владельцы доменов, классификация, согласование модели доступа и ограничений размещения | У каждой переносимой функции есть владелец, источник истины, контракт и способ сверки; запрещённые источники исключены |
| 0–6 месяцев | Пилот каталога и одного разрешённого продукта; ACL-адаптер старой системы, портал, публикация, аудит, восстановление | Сверка контрольных сумм/финансовых итогов, негативные проверки доступа, нагрузочный профиль и восстановление подтверждены на стенде |
| 6–12 месяцев | Портал доступен основным бизнесам; несколько продуктов клиник, банка, производства, заявка на новый срез; обучение владельцев | Портал и доменный доступ работают в первый год; согласованные сценарии не требуют новой логики в общем DWH |
| 12–18 месяцев | Перенос следующих функций из PowerBuilder/DWH, разделение моделей, новые производства, наблюдаемость продуктов | Для каждой функции завершена сверка и переключён единственный писатель; старый маршрут используется только для оставшихся функций |
| 18–36 месяцев | Подключение регионов и новых компаний по шаблону продукта, вывод оставшихся общих бизнес-процедур и Camel-маршрутов | Нет активных потребителей отключаемых маршрутов; архив и восстановление проверены, источник истины документирован |

SQL Server 2008 не считаю автоматически совместимым с современным CDC-коннектором. Сначала проверяется конкретная версия и способ чтения. Для пилота допустимы контролируемый инкрементальный экспорт или прикладной журнал с high-water mark и сверкой; потребители учитывают повтор и запоздалую корректировку. При отсутствии надёжной дельты сначала обновляется источник либо делается согласованная пакетная выгрузка разрешённой проекции, а не непрерывная копия всех таблиц.

Миграция функции: фиксирую исходные итоги → делаю начальную загрузку и догоняющую дельту → сравниваю результат на контрольном периоде → ограничиваю изменения на время переключения → меняю маршрут и единственного писателя. Теневой расчёт допустим, двойная запись двумя независимыми приложениями — нет. До первой записи в новую систему можно вернуть старый маршрут; после неё возврат требует обратной миграции накопленных изменений и сверки, а не простого переключения DNS.

## Размещение, рост и проверяемые цели

Это логическая схема. До выбора площадок нужно согласовать, какие продукты и копии могут пересекать регионы. Клинические данные не реплицируются через аналитическую платформу. Для доменов выбирается владеющий регион, а общий каталог маршрутизирует к разрешённой региональной витрине. Отказ региона не должен приводить к запросу запрещённой копии в другом регионе.

Для продуктивной платформы планируются независимые реплики stateless-приложений, отказоустойчивая конфигурация PostgreSQL/Kafka/ClickHouse, резервные копии и регулярное восстановление. Конкретное число узлов, размещение и тип managed/self-hosted выбираются после нагрузочного профиля и TCO. Реплика не заменяет резервную копию. ВМ dev/stage/prod из учебного Terraform не являются доказательством такой отказоустойчивости.

Начальные цели для пилота, **не измеренные результаты и не подтверждённые SLA**:

- API портала: p95 до 2 секунд для типовых агрегатов, таймаут запроса 30 секунд; тяжёлые выгрузки — отдельные задания с квотами.
- Разрешённые оперативные продукты: свежесть до 15 минут; корпоративные закрытия — по согласованному календарю периода. Просроченный продукт помечается, а не выдаётся как актуальный.
- Аналитика: доступность 99,5% в месяц; восстановление каталога и политик RTO 4 часа, RPO 1 час. Потерянные записи публикаций восстанавливаются сверкой с доменными манифестами, доступ не открывается до сверки.
- Перед пилотом: негативная матрица доступа, чужая организация/регион, отзыв во время выгрузки, повтор события, неизвестное поле, сбой загрузчика и восстановление из копии.

Эти цели согласуются с владельцами и проверяются на данных стенда. Для банка и медицинских операций нужны собственные требования; переносить на них допустимый простой портала нельзя.
